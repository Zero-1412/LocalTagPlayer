# 播放器流畅性标准与项目门禁（2026-08-20）

## 结论先行

“流畅”没有一个可以直接套用到所有本地播放器的单一分数。公开规范提供的是
可观测指标和语义；具体的 `200 ms`、`500 ms` 等交互时延必须作为本项目的工程门禁，
不能冒充国际标准。本项目从现在起同时使用两层标准：

1. **规范语义层**：实际呈现帧、解码/VO 掉帧、展示延迟、卡顿事件和硬解能力必须分层
   记录；Dart 命令完成、`time-pos` 或帧号代理不能代替屏幕上的第一帧。
2. **项目门禁层**：在固定 Debug 构建、固定素材、固定显示器和固定输出路径下，用
   p50/p95、最长无变化区间和掉帧趋势做可重复判定。任何 `unknown` 都不能写成通过。

## 规范依据

| 来源 | 可采用的定义 | 对本地播放器的落地 |
| --- | --- | --- |
| [W3C Media Capabilities](https://www.w3.org/TR/media-capabilities/) | `smooth` 只有在目标帧率下解码且不丢帧时才为真；配置包含编码、尺寸、码率和帧率 | 每个 H.264/HEVC/AV1、1080p/4K case 必须记录实际帧率、硬解状态和掉帧；不能只看“支持” |
| [W3C Media Source Extensions / VideoPlaybackQuality](https://www.w3.org/TR/2016/CR-media-source-20160503/) | 区分总帧、掉帧、损坏帧，并累计展示帧延迟；掉帧还包括错过显示截止时间的已解码帧 | 记录 decoder drop、VO drop、total drop，并把“解码完成但未按时显示”归到 VO/呈现段，而不是只看解码器 |
| [mpv reference manual](https://mpv.io/manual/master/) | `framedrop=vo` 是推荐默认；`video-sync=display-resample` 尝试避免跳帧/重复帧；显示同步受 VO、驱动、刷新率影响，切换全屏或缩放时可能跳帧 | Texture 重建、全屏和 DPI 变更单独测；不能用一次 seek 命令耗时推断连续呈现 |
| [ITU-T P.1203](https://www.itu.int/itu-t/recommendations/rec.aspx?lang=en&rec=13399) | 每秒短期音视频质量、初始加载延迟和 stalling 事件共同影响整体质量 | 本地文件也记录首播首帧、动作后卡顿区间和恢复时间；不把“命令返回”当作质量终点 |
| [Android 13 CDD](https://source.android.com/docs/compatibility/13/android-13-cdd) | 在其定义的受载 1080p60 场景中，视频掉帧不得超过每 10 秒 1 帧 | 只作为掉帧数量的外部参考上限；它不是 Windows 本地播放器的通用合规承诺，仍需报告证据窗口 |

## 工程门禁（本机可执行）

下列数值是本项目面向“接近专业播放器体感”的回归门槛，不是规范原文。门禁使用
**首个实际 DWM/桌面合成变化**，不是 Dart `Future` 完成；长按首帧必须发生在按住期间，
`Up→首帧` 在松键后才出现时只能作为恢复指标，不能伪造为按住期间的连续扫描。

### 稳态播放（至少 10 秒，独立于 seek）

- decoder drop：`0`；VO drop：`0`。任一非零都进入失败分析，不允许用平均值掩盖。
- total drop：优先 `0`；若测试环境必须有受载扰动，参考 Android CDD 的数量级，
  10 秒最多 `1` 帧（1080p60）。没有明确秒数的 action-window 计数只能记为 `unknown`。
- 展示节奏：以实际内容帧率 `F` 计算期望周期 `1000/F`；有可靠逐帧呈现时间时，
  p95 间隔不超过 `1.5 ×` 期望周期，最大间隔不超过 `3 ×`。匿名像素指纹只能证明
  “屏幕在变化”，不能冒充逐帧计数，因此只能作为辅助证据。
- 卡顿：稳态不允许超过 `250 ms` 的无新画面区间；stalls/总时长应为 `0`。
- Texture generation/尺寸：稳态窗口内不得重建；启动、全屏、DPI 变更发生重建时，
  必须单列重建耗时，不能混入稳态掉帧。

### 交互门禁（同机固定 Debug 构建）

| 动作 | p95 首个实际呈现帧 | 额外要求 |
| --- | ---: | --- |
| 首次播放 | ≤ `1000 ms` | 记录首个 DWM 帧、硬解和 Texture 代次；没有 DWM 证据为 `unknown` |
| 短按前进/后退 | ≤ `250 ms` | 关键帧语义必须明确；落点精度另测，不把关键帧预览写成精确定位 |
| 拖动预览 | ≤ `500 ms` | 松手后准确收敛 p95 ≤ `300 ms`；必须有 Slider `onChangeEnd` 回执 |
| 长按前进/后退 | ≤ `300 ms` | 按住期间最长无变化 ≤ `500 ms`；前后均须有独立合同 |
| 全屏/窗口切换 | 几何稳定 ≤ `100 ms` | 切换前后 Texture 尺寸/代次、DPI 和显示器单列；不能用几何变化代替视频帧 |

长按的“专业级连续扫描”还有一条比首帧更严格的呈现门禁：在 60fps 内容上，连续
呈现变化的 DWM 辅助证据 p95 间隔应 ≤ `50 ms`、最大间隔 ≤ `100 ms`，且每次有效轮次
至少观察到 5 个后续变化。若只能拿到匿名指纹而没有逐帧时间戳，结果只能是
`not-proven`；反向 latest-only 关键帧预览不得冒充双向连续扫描通过。

### 证据分级和最终判定

- `pass`：所有适用门禁均通过，且动作语义、DWM 呈现、运行态和资源释放证据齐全。
- `fail`：任一适用门禁超标，或页面语义/资源释放失败。失败样本不进入 p50/p95，
  但必须保留以定位根因。
- `unknown`：只有后端帧代理、缺少稳态时长、缺少实体 QPC、缺少 VO/逐帧时间戳或
  另一输出路径不可用。`unknown` 不能写成“流畅”。
- `not-applicable`：当前产品合同明确不是该体验，例如短按不要求连续扫描；必须在报告
  中写出替代语义（关键帧预览、松手精确收敛等）。

`tool/evaluate_player_smoothness_standard.ps1` 会读取匿名桌面矩阵/单动作报告，计算
上述门禁并输出 JSON。它只生成 QA 证据，不改变播放器业务、后端默认选择、Texture 档位
或用户数据。

## 当前证据按标准的初判

- 1080p AV1 长按前进：首帧 p95 约 `1105 ms`、最长无变化约 `950 ms`，连续扫描门禁
  **失败**；这与用户感知的卡顿一致，根因仍在首帧前的解码/VO/Texture 合成链。
- 4K AV1 反向长按：单轮首帧 `273 ms` 只能通过首帧预算的单样本观察；后续 5 个匿名
  呈现变化间隔约 `126 ms`，连续扫描门禁 **失败/不适用需拆开**，只能称为 latest-only
  关键帧预览，不能称为专业级双向扫描。
- 4K 三编码短按的现有 p95 大多在 `250 ms` 内，但它们主要是自动化输入；实体
  `WM_KEYDOWN/QPC → DWM` 长按 p50/p95 仍未形成完整矩阵，因此实体门禁为 `unknown`。
- 现有矩阵的 `totalDropFramesMax` 是动作窗口计数，缺少 10 秒稳态分母；依据规则只能
  记为 `unknown`，不能拿 `0` 或“最终硬解”替代稳态掉帧结论。

## 停止条件

本机阶段在每个 codec/分辨率/动作至少 3 个有效独立会话、失败不混入统计、报告同时
包含语义/DWM/运行态/资源释放后停止重复跑同一动作。仍标为 `unknown` 的实体输入、
发布 GPU、HWND 公平 A/B 和逐帧可见性属于外部验收清单，不再以无限等待脚本作为完成条件。
