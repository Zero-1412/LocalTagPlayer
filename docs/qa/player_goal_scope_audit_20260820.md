# 播放器真实性能目标范围审计（2026-08-20）

## 结论

当前目标方向没有错：先用真实窗口把输入、解码、VO、Texture 和 DWM 呈现拆开，再决定
是否调整正式渲染架构。但把性能基线、根因修复、原生 HWND 对照、真人键盘时序、发布级
硬解矩阵以及五项专业控制全部放进同一个“全部完成才结束”的终止条件，导致任务没有
可判定的停止点。12 小时仍未结束，主要是目标和验收合同设计问题，不是某一个 Dart
函数尚未再节流一次。

本审计不降低原始 P0/P1 要求，只把证据等级和所需外部条件分开；未取得强证据的项目仍
标记为未完成，不以自动化代理替代真人或以 Debug 结果替代发布矩阵。

本轮已补上之前缺失的“流畅”判定层：公开规范只定义无掉帧、展示延迟、加载/卡顿等
指标，并不提供本地播放器 seek 的统一毫秒数；因此项目把规范语义和本机工程门禁分开，
详见 `docs/qa/player_smoothness_standard_20260820.md`。当前已有报告可以由
`tool/evaluate_player_smoothness_standard.ps1` 重放评估；评估结果为 `fail/unknown` 时
不得用“命令完成”或后端帧代理覆盖。

## 要求与证据边界

| 要求 | 当前最强证据 | 仍缺什么 | 类型 |
| --- | --- | --- | --- |
| 输入到实际 DWM 帧 | 正式 PlayerPage/Texture；H.264 4K 自助原生短按 7/7；自动化三编码矩阵 | 实体长按 Down/Up QPC p50/p95；不能由 `press_key` 保持键态 | 外部输入条件 |
| 反向 seek 分段 trace | 已有 cache、decoder、VO、Texture generation、帧代理和 `reverse_preview_frame_wait_*`；刚构建 4K AV1 单轮实际 DWM 273ms、5 个后续变化 | 三编码独立矩阵、每个目标的屏幕帧关联；4K AV1 曾有全 7 轮失败，不能混算 | 代码 + 运行矩阵 |
| 4K/高刷新率/全屏/DPI | 实机 `3840×2160 @160Hz / 144DPI` 显示器清单；三编码 Texture generation/尺寸重建和全屏几何证据 | 真实跨物理屏移动/跨 DPI 窗口确认；这不是单机脚本能凭显示器清单证明的 | 外部窗口条件 |
| 短按/拖动/长按合同 | 三编码正式 Texture 自动化语义矩阵，拖动含 Slider 回执；长按含按住期间采样 | 真人时序合同和专业级体验阈值未定义 | 验收定义缺失 |
| 硬解降级 | Debug 强制软件解码 H.264/HEVC/AV1，`hwdec=no`、用户可见恢复动作和安全重开 | 非强制回退、发布构建、不同 GPU 的概率和预算 | 外部硬件条件 |
| 可调倍速 | PlayerPage 设置入口、`PlayerService.setRate`、快捷键和状态持久化链路 | 真实窗口倍速节奏预算；QA 不能只读属性就宣称播放速度体验 | 代码 + 运行矩阵 |
| 双向连续扫描 | 前进使用临时扫描档位；后退是按帧让渡的 latest-only 关键帧预览；1080p 有多次 DWM 变化 | 真正对称的连续反向解码不可由当前 mpv `play-direction=backward` 可靠提供；需要明确产品语义或替代解码方案 | 产品/架构决策 |
| 逐帧/A-B/外挂字幕 | 三编码真实 PlayerPage 命令、属性/轨道回读和资源释放 QA | 逐帧 DWM、A-B 实际重复播放、字幕可见性/同步 | 运行验收 |
| Texture vs HWND | 同机报告保留两后端失败差异；HWND 精确 seek/首帧确认不稳定 | 可公平比较的等价 HWND 输出路径；不能用失败 HWND 证明 Texture 必然根因 | 平台实现条件 |

## 为什么原目标会无限延长

1. “丝滑”没有统一数值门槛。不同脚本混用 `1.0%/1.5%` 像素阈值、80fps 采样门槛、
   250ms 观察窗和不同样本数；p95 的样本量、预算、失败重试规则没有在目标中固定。
2. “不改业务功能的基线”与“基线稳定后再实现五项功能”共用同一个活动目标。AV1 长尾
   还未解决时，后续功能既不能开始，也不能把目标标记完成，形成依赖环。
3. 代码修改、真实窗口、真人输入、另一套原生后端、不同 GPU 和远端 push 被视为同一
   agent 可独立完成的工作；其中至少三项需要外部状态或硬件，不能靠继续运行脚本消除。
4. 本机媒体路径和 GPU 状态不进入仓库，统一 12-case manifest 也没有固定版本；每次新
   会话都可能重新选择素材或遇到 Texture/单实例冷却，从而制造新的“还需再跑一轮”。
5. 当前历史记录把已完成、失败、无效和待办混在同一 `CURRENT_TASK.md`，容易把旧的
   `2.7s` 位置确认数字、旧基线失败和新 DWM 证据反复当成同一问题。

## 有限停止条件

### 本仓库/本机可关闭的阶段

- 以当前 Debug 可执行文件固定一份匿名 manifest；每个编码/分辨率/动作至少 3 个独立
  有效会话，失败会话不进入 p50/p95；报告必须同时列出输入语义、DWM 首帧、后续呈现
  变化、cache/decoder/VO/Texture、硬解和资源释放。
- 正式 Texture 的短按、拖动、自动长按、全屏和 4K/DPI 结构证据写成单一报告；不把
  估算帧号或位置完成冒充 DWM 帧。
- 反向扫描只宣称“按帧让渡的关键帧预览”，除非另有可观测的连续反向解码实现；当前
  4K AV1 反向若三轮不能稳定形成 DWM 帧，应记录为产品限制而停止重复重跑。
- 专业控制先分为“命令/资源 QA”与“可见性 QA”，两者均记录证据等级；不得用前者
  覆盖后者。

### 需要外部条件的阶段

- 真人实体长按：需要真实 key-down/key-up 保持接口或人工操作，不由 agent 的单次
  `press_key` 伪造。
- Texture/HWND 公平 A/B：需要稳定、可播放、同一素材的 HWND 后端；若 HWND 自身首帧
  和 seek 合同失败，结论应是“HWND QA 路径不可发布”，而不是继续调 Texture。
- 非强制硬解发布矩阵：需要目标 GPU/驱动和发布构建运行环境。

## 当前决策

从现在起不再以“再跑若干自动矩阵”作为无期限工作。当前任务应拆成三个可交付物：

1. **P0 证据包**：正式 Texture 的输入/DWM/trace/Texture 重建报告和已知限制；
2. **P1 控制包**：命令 QA、可见性 QA、反向扫描语义和明确的未实现/不支持边界；
3. **外部验收清单**：真人长按、HWND A/B、发布 GPU 回退，由具备条件的环境单独关闭。

在三个交付物分别达到上面的停止条件前，不能声称“全部完成”；达到本机停止条件后，
本 agent 应停止重复测量并报告外部验收项，而不是继续运行到新的时间上限。
